# Situação Atual

Após definir a estratégia da feira, concluímos que nosso objetivo não é desenvolver um software comum, mas sim construir uma **experiência memorável**.

A tecnologia existe apenas para possibilitar essa experiência.

Portanto, todas as decisões futuras devem priorizar a experiência do visitante acima da complexidade técnica.

---

# Mudança de foco

Não queremos responder:

> "Como fazemos um software interessante?"

Queremos responder:

> "Como fazemos alguém pensar no projeto horas depois de sair da feira?"

---

# Objetivo Principal

Criar uma experiência que desperte:

- curiosidade;
- descoberta;
- cooperação;
- comparação;
- interpretação;
- incerteza.

Sem depender de sustos, violência ou narrativa explícita.

---

# Referências Conceituais

Estas referências NÃO devem ser copiadas visualmente nem narrativamente.

Devem servir apenas para entender as sensações que queremos provocar.

## ENA

- caos com lógica própria;
- sensação de que o mundo possui regras desconhecidas;
- estranhamento constante.

---

## Cube Escape / Rusty Lake

- objetos comuns em situações incomuns;
- narrativa fragmentada;
- descoberta através da exploração;
- poucas explicações.

---

## Backrooms

- liminaridade;
- espaços silenciosos;
- sensação de familiaridade quebrada;
- desconforto sem motivo evidente.

---

## ARGs e Cicada 3301

- descoberta coletiva;
- sensação de existir algo escondido;
- comunidade criando teorias;
- usuário sente que está descobrindo, não recebendo respostas.

---

# Princípio Fundamental

O visitante nunca deve sentir que está consumindo uma história.

Ele deve sentir que está investigando um sistema.

---

# Ideia Atual

Ao invés de criar um jogo tradicional, criar um software fictício de catalogação.

O visitante acredita que está registrando informações sobre um determinado local.

Na realidade, o programa gradualmente demonstra que:

- os registros nunca são totalmente consistentes;
- duas pessoas nunca recebem exatamente a mesma experiência;
- pequenas diferenças surgem constantemente;
- existe uma lógica, mas ela nunca é completamente explicada.

---

# Os dois notebooks

Os notebooks NÃO são duas cópias do mesmo programa.

Eles fazem parte do sistema.

Cada notebook possui:

- informações diferentes;
- documentos diferentes;
- pequenas alterações;
- observações exclusivas.

Os dois usuários precisam conversar para perceber que existem inconsistências.

Essa cooperação deve surgir naturalmente.

---

# O verdadeiro conflito

O conflito não é:

"Como vencer?"

O conflito é:

"Qual versão da realidade está correta?"

---

# O motor da experiência

O programa observa discretamente o comportamento do usuário.

Exemplos:

- tempo parado;
- ordem dos cliques;
- objetos ignorados;
- mudanças de decisão;
- insistência em determinados elementos;
- interação com o outro notebook.

Essas informações alteram pequenos detalhes da experiência.

Nunca mudanças gigantes.

Sempre alterações sutis.

---

# Filosofia das mudanças

O programa nunca deve parecer aleatório.

Toda mudança deve dar a impressão de que existe uma regra.

Mesmo que essa regra nunca seja totalmente revelada.

---

# O visitante deve criar teorias

Queremos que o visitante pense coisas como:

"Será que aconteceu porque cliquei nisso?"

"Será que o notebook dele mostrou outra coisa?"

"Será que o programa lembra das escolhas anteriores?"

"Será que o prédio mudou?"

Não responder essas perguntas imediatamente.

---

# Engenharia Invisível

A engenharia não deve existir apenas para impressionar jurados.

Ela deve justificar a experiência.

Exemplos:

- estado compartilhado entre notebooks;
- persistência entre sessões;
- sistema de eventos;
- regras invisíveis;
- geração dinâmica de conteúdo;
- observação do comportamento do usuário.

---

# Leis do Mundo

Estas regras nunca devem ser quebradas.

1. O programa nunca confirma que algo mudou.

2. O programa nunca diz que existe um mistério.

3. Não existem jumpscares.

4. Não existem monstros.

5. O desconforto deve surgir apenas através da atmosfera.

6. Nenhuma informação explica tudo.

7. Toda resposta deve gerar pelo menos uma nova pergunta.

8. Pequenas mudanças são mais importantes que grandes mudanças.

9. O usuário nunca possui todas as informações.

10. Os dois notebooks nunca possuem exatamente a mesma realidade.

---

# Estética

Preferências gerais:

- interface institucional;
- aparência de software antigo;
- poucos elementos;
- muito espaço vazio;
- tipografia simples;
- sons discretos;
- animações lentas;
- cores pouco saturadas.

Evitar interfaces chamativas.
