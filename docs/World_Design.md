# WORLD_DESIGN.md

> Documento responsável por definir a lógica do universo do projeto.
>
> Este documento NÃO contém código.
>
> Ele define apenas as regras do mundo, seus comportamentos e sua filosofia.
>
> Toda implementação futura deve respeitar este documento.

---

# Objetivo

O usuário não deve sentir que está jogando.

Ele deve sentir que entrou em um sistema que já existia antes dele chegar.

O programa não conta uma história.

O programa existe.

O visitante apenas entra nele.

---

# Filosofia

O projeto deve gerar uma sensação constante de:

- curiosidade
- estranhamento
- descoberta
- dúvida
- interpretação

Jamais:

- medo explícito
- violência
- jumpscares
- terror convencional

O desconforto nasce da inconsistência.

---

# A grande pergunta

O usuário nunca tenta descobrir:

"Quem fez isso?"

Ele tenta descobrir:

"Como esse lugar funciona?"

---

# O Mundo

O projeto acontece dentro de um ambiente digital fictício.

Esse ambiente aparenta ser um software institucional.

Não sabemos:

- qual empresa criou;
- qual governo criou;
- para que ele realmente serve.

O visitante apenas recebe acesso.

---

# O Prédio

Existe um único edifício.

Esse edifício possui diversas salas.

O problema:

Nenhum registro do prédio é totalmente consistente.

---

Exemplo

Documento A:

Sala 17 possui uma janela.

Documento B:

Sala 17 nunca teve janela.

Os dois documentos são oficiais.

---

# Regra Principal

Nenhuma informação pode ser considerada absolutamente verdadeira.

---

# O Sistema

O sistema acredita estar funcionando normalmente.

Ele nunca diz que existe erro.

Nunca aparece:

"Falha"

"Erro"

"Bug"

Para o sistema:

Tudo está correto.

---

# O Visitante

O visitante possui uma única função.

Catalogar.

Nada mais.

---

# Objetivo Aparente

Registrar:

- salas
- objetos
- observações
- fotografias
- documentos

---

# Objetivo Real

Não existe.

O usuário cria seu próprio objetivo.

---

# O Programa observa

Durante toda a experiência o sistema registra:

- ordem dos cliques
- tempo parado
- objetos favoritos
- mudanças de decisão
- retorno para salas antigas
- interação com outro notebook

Essas informações modificam discretamente a experiência.

---

# Tipos de Mudança

Nunca grandes.

Sempre pequenas.

Exemplos

Uma cadeira desaparece.

Uma palavra muda.

Uma fotografia possui um detalhe diferente.

Uma sala muda de número.

Um documento aparece.

Outro desaparece.

Uma data muda.

Uma assinatura muda.

Uma porta muda de lado.

---

# O Programa nunca comenta

Jamais escrever:

"Algo mudou."

O programa continua normalmente.

---

# Estado Global

Existe apenas um mundo.

Todos os visitantes compartilham esse mundo.

Os notebooks apenas enxergam partes diferentes dele.

---

# Os Dois Notebooks

Eles nunca são idênticos.

Nunca.

Mesmo na primeira tela.

Sempre existe pelo menos uma diferença.

Mesmo que pequena.

---

# Comunicação

Os usuários descobrem naturalmente que:

os dois programas discordam.

Não é a equipe que conta.

Eles percebem.

---

# Informações

Nenhum notebook possui todas.

Notebook A sabe coisas que B nunca verá.

Notebook B sabe coisas que A nunca verá.

Somente conversando eles aproximam a verdade.

---

# Verdade

Não existe verdade absoluta.

Existem versões.

---

# Atmosfera

Silêncio.

Pouca música.

Poucas animações.

Muito espaço vazio.

Poucas cores.

Interface limpa.

Tudo parece comum.

Mas nunca totalmente normal.

---

# Ritmo

A experiência nunca acelera.

Ela apenas aprofunda.

O visitante deve sentir que:

quanto mais entende,

menos compreende.

---

# Objetos

Objetos comuns.

Nunca mágicos.

Exemplos

Mesa.

Arquivo.

Telefone.

Lâmpada.

Relógio.

Janela.

Escada.

Mapa.

Fotografia.

Cadeira.

Esses objetos mudam discretamente.

---

# Eventos

Os eventos nunca parecem roteirizados.

Eles parecem consequência.

Mesmo quando não forem.

---

# Engenharia Invisível

Toda funcionalidade técnica deve existir para reforçar a ilusão.

Nunca implementar tecnologia apenas para impressionar.

---

# O usuário deve pensar

"Será que fui eu?"

"Será que aconteceu antes?"

"Será que no notebook dele apareceu igual?"

"Será que cliquei errado?"

"Será que esse documento sempre esteve aqui?"

---

# O programa nunca responde.

---

# O Final

Não existe um final definitivo.

Existe apenas um encerramento.

Os usuários saem com interpretações diferentes.

---

# O papel da equipe

A equipe nunca entrega respostas imediatamente.

Primeiro pergunta.

Depois escuta.

Só então explica a engenharia.

Nunca explica completamente a narrativa.

---

# Regras Absolutas

1. Nunca confirmar mudanças.

2. Nunca explicar toda a lógica.

3. Nunca usar terror barato.

4. Nunca quebrar a estética.

5. Nunca mostrar toda a informação.

6. Sempre deixar espaço para interpretação.

7. O sistema sempre acredita estar correto.

8. O usuário nunca sabe se influenciou o mundo.

9. O mundo parece maior do que realmente é.

10. Toda implementação futura deve obedecer estas regras.
